# G-07 阶段一验收准入治理设计

> 状态：方案 1 已于 2026-07-18 确认。仓库代码、PRD 缺口分析、Flyway 结果和自动化测试是事实来源；不得用研发推断代替业务验收责任。

## 1. 目标与准入口径

G-07 是正式开发 v0.2 阶段一前的“验收输入准备”门禁，要求阶段一 E2E 场景、黄金测试数据、验收引用映射和验收责任已经形成可评审、可追踪的版本。G-07 不要求尚未开发的业务全链已经执行成功；真正的 E2E 执行结果属于后续模板投产门禁。

以下内容不能使 G-07 自动通过：

- 仅验证静态前端和 Mock API 的 Playwright 用例；
- 只有 `AT-*` 编码但没有场景、数据和验收责任的定义包；
- 没有独立评审的人工说明、聊天记录或临时文件；
- 平台单元测试、Todo Engine 技术测试或既有业务页面契约测试。

## 2. 仓库事实基线

- PRD 阶段一覆盖销售主链路、案管分类和综法最小闭环。
- 阶段一模板范围固定为 `TD-001`～`TD-016`、`TD-022`、`TD-023`、`TD-025`，共 19 个模板。
- 每个模板包含 `OWNER`、`SLA`、`DOD`、`ROUTE`、`HANDLER`、`UI` 六类验收引用，共 114 个唯一 `AT-*`。
- 上述 19 个定义文件中验收引用在 envelope 和规范定义各出现一次，因此仓库文本出现 228 次不等于 228 个验收项。
- 当前 Playwright 共 28 个用例，均通过静态 `dist` 和 Mock `/prod-api` 运行；没有任何用例绑定 `AT-TD-*`。
- `G07-PHASE-ONE-ACCEPTANCE` 当前为 `OPEN`，没有专用就绪计算、黄金数据、AT 映射或审批防误通过逻辑。

## 3. 方案选择

采用“严格的开发准入证据账本”。它在开发前确认未来如何验收，但不伪造未来执行结果。

未采用：

1. **要求真实全链先通过再允许开发**：会形成“必须先完成开发才能开始开发”的循环。
2. **用现有 28 个 Mock E2E 抵扣 G-07**：这些测试没有真实后端、数据库、业务状态或 Todo 状态，证据强度不足。
3. **只建一张全局检查表**：无法证明 114 个 AT 引用逐项有场景和责任，后续容易出现模板遗漏。

## 4. 数据模型

所有表通过新的前向 Flyway 迁移创建，不修改已执行迁移。

### 4.1 `todo_foundation_acceptance_requirement`

保存 G-07 固定要求及仓库来源，至少包含：

- 阶段一 19 模板范围；
- 114 个 AT 引用目录；
- 阶段一场景清单；
- 黄金数据版本与校验和；
- 114/114 AT 到场景映射；
- 业务验收人分配；
- 独立评审签字；
- Mock 测试与真实执行证据分离。

固定要求记录只能描述事实来源和检查类型，不能写入业务结论或虚构签字。

### 4.2 `todo_acceptance_scenario`

保存阶段一验收场景版本：

- 稳定 `scenario_code`、名称、阶段和业务链路；
- 前置条件、操作步骤和预期结果的版本化 JSON；
- `dataset_ref`、`dataset_checksum` 和数据版本；
- 业务 Owner、业务验收人、独立 Reviewer 和截止时间；
- `DRAFT`、`IN_REVIEW`、`APPROVED`、`REJECTED` 状态；
- 乐观锁版本、创建/修改/评审审计。

至少需要一个稳定编码为 `PHASE_ONE_GOLDEN_PATH` 的场景，明确覆盖“线索接入→客户/合同→转案→案管分类→综法办理→归档”。场景内容由 PRD 和授权业务负责人确认，迁移不得自动生成业务步骤。

### 4.3 `todo_acceptance_ref_mapping`

从 `todo_prd_definition_catalog.acceptance_refs_json` 初始化 19 个模板的 114 个映射槽位：

- `acceptance_ref` 为唯一键；
- 保存模板编码和六类验收维度；
- `scenario_id`、计划测试引用和证据说明初始为空；
- 状态为 `UNMAPPED`、`MAPPED`、`IN_REVIEW`、`APPROVED` 或 `REJECTED`；
- 保存 Owner、Reviewer、截止时间、评审结论和乐观锁版本。

初始化映射槽位不代表验收通过。只有关联已批准场景、计划测试引用完整且由独立 Reviewer 批准后，单个 AT 才计入 G-07 覆盖率。

### 4.4 幂等动作账本

场景与映射写操作共用专用动作账本或等价的 `actionId` 机制，记录请求指纹、操作者和应用状态。重复请求只返回既有结果，不重复变更证据状态。

## 5. 后端边界与就绪算法

新增 `TodoAcceptanceReadinessService`，只读计算：

- 阶段一模板是否恰为 19 个；
- 唯一 AT 是否恰为 114 个且命名、模板和维度一致；
- 场景总数、已批准场景数和黄金场景状态；
- 有有效黄金数据引用与校验和的已批准场景数；
- 114 个 AT 的映射、评审和批准数量；
- 业务验收人、独立 Reviewer 和截止时间完整性；
- G-07 固定要求的 `READY`、`SOURCE_UNRESOLVED`、`RUNTIME_MISSING`、`RUNTIME_INCOMPLETE` 数量。

`gateReady("G-07")` 只有同时满足以下条件才返回 `true`：

1. 阶段一范围为 19 个模板、114 个唯一 AT；
2. `PHASE_ONE_GOLDEN_PATH` 已批准且具有数据引用、版本和校验和；
3. 所有已纳入范围的场景均有业务 Owner、业务验收人、独立 Reviewer 和截止时间；
4. Owner/验收人不能代替独立 Reviewer；
5. 114/114 AT 均关联已批准场景和计划测试引用，并完成独立评审；
6. 所有 G-07 固定要求为 `READY`。

`TodoAdmissionEvidenceService` 在批准 `G-07` 前调用该门禁；不满足时返回稳定错误码 `TODO_ADMISSION_ACCEPTANCE_NOT_READY`。批准 G-07 不自动发布模板、不启用触发规则，也不改变 `production_state`。

## 6. API 与权限

读取接口复用 `todo:admission:view`：

- `GET /todo/foundation-acceptance`：汇总、固定要求、场景和 AT 覆盖率；
- `GET /todo/acceptance-scenarios`：场景列表；
- `GET /todo/acceptance-mappings`：按模板、维度、状态筛选 114 个映射。

写接口复用 `todo:admission:edit`：

- 新增/修改场景、提交评审、批准、拒绝和重新打开；
- 绑定 AT 到场景、填写计划测试引用、提交评审、批准和拒绝；
- 批量绑定只能批量设置场景或测试引用，不能批量伪造 Reviewer 结论。

所有写接口使用强类型 DTO、Bean Validation、`actionId`、期望版本、功能权限和独立评审校验。迁移不自动授予角色权限。

## 7. 前端设计

Todo 配置中心新增“阶段一验收”页签：

- 汇总 19 个模板、114 个 AT、已映射、已评审、场景和黄金数据就绪数量；
- 明确显示“现有 28 个 Mock E2E 不计入 G-07”；
- 场景列表与版本化编辑/评审抽屉；
- AT 映射表，支持模板、六类维度和状态筛选；
- 未分配 Owner、验收人、Reviewer、截止时间和逾期提示；
- G-07 未就绪时显示具体缺口并说明不能批准准入证据。

页面不提供“自动全部通过”操作，也不把仓库中存在测试文件等同于验收引用已映射。

## 8. 状态、并发和错误处理

- 场景与映射遵循 `DRAFT/UNMAPPED → IN_REVIEW → APPROVED|REJECTED`，被拒绝后可重新提交；
- 已批准记录不可由普通编辑直接覆盖，变更需重新打开并产生新版本或重新评审；
- 条件更新失败返回版本冲突，不覆盖他人评审；
- Owner、验收人和 Reviewer 必须是有效用户；Reviewer 必须独立；
- 场景缺少步骤、预期结果、数据引用或校验和时不能提交评审；
- 映射缺少场景或计划测试引用时不能提交评审；
- 所有动作写不可变审计，不删除历史评审证据。

## 9. 测试与验证

所有新增行为测试先行：

- 服务单元测试：19/114 范围、来源/运行态差距、完整门禁和边界值；
- 状态机测试：场景/映射提交、批准、拒绝、重新打开、独立 Reviewer、版本冲突和幂等；
- 迁移契约：只初始化 114 个未映射槽位，不产生场景、黄金数据、用户、签字或模板发布；
- API 权限与 Bean Validation 测试；
- G-07 准入证据审批防误通过测试；
- 前端契约、UTF-8、生产构建和 Playwright；
- Playwright 覆盖场景登记、AT 绑定、评审状态、筛选、刷新持久化和门禁提示；
- 真实 MySQL 从 v0.15 基线执行全部 Flyway，并验证唯一键、检查约束、114 项目录和零伪造证据；
- 全量 Maven、前端契约、Schema、构建和 E2E 回归。

## 10. 完成定义与后续边界

本切片完成时：

- G-07 的场景、黄金数据、AT 映射和责任可以由授权人员管理、评审并可视化；
- 后端可以可靠阻止未闭环 G-07 被批准；
- 当前仓库会如实显示 G-07 未就绪，不会因 28 个 Mock E2E 自动变绿；
- 仓库具备后续由业务/QA 补齐并关闭 G-07 的完整工具。

G-07 真正变为 `READY` 仍需要授权人员提交并批准场景、数据和责任证据。正式 v0.2 实现后，真实全链 E2E 的执行记录进入模板投产门禁，不回写或篡改开发准入时的历史证据。
