## 1. 结论

现有系统已经具备进入 v0.2 开发的技术基础，但尚未具备直接按 PRD 验收的业务能力。

- Todo Engine 底座：可复用。模板版本、触发规则、Owner、DoD、SLA、工作日历、通知、异常处置、业务链路视图和 Outbox 已具备。
- 既有业务骨架：可扩展。线索、客户、合同、收费计划、案件分配、事项节点、文档、费用、结案归档均已有表和页面。
- 主要缺口：案管分类与三路分流、非诉独立流程、执行独立流程、无效分级、外呼留痕、节点型应收、风险代理催收、文件中心鉴权、绩效计算。
- 当前可复用的标准模板为 14 个，PRD 要求 25 个业务模板；两者并非简单的 14/25 覆盖，部分模板需拆分或重新定义 DoD/SLA/Owner。
- 建议按两阶段实施：阶段一完成销售主链路与案管分类/综法最小闭环；阶段二完成非诉、执行、风险代理、绩效和深度合规能力。

## 3. Todo Engine 必须扩展的组件

### 3.1 P0 组件

1. **流程路由上下文**：统一提供 `businessLine`、`caseCategory`、`nonLitigationTags`、`executionServiceType`、组织层级和收费模式，供触发条件与 Owner 计算使用。
2. **循环/周期待办**：支持完成后按规则生成下一周期，适用于 5 天跟进、T+1/T+2 重试、立案 10 日跟进、裁判文书 30 日跟进、执行 5/15/30 日上报。
3. **超时自动动作**：除提醒/升级外，支持“24h 超时默认通过”等受控动作；必须记录规则版本、执行账号和动作日志。
4. **分支与汇聚**：支持有效/疑似无效/无法联系、线上/线下签章、非诉/综法/执行、接单/拒接、调解和解直达结案。
5. **DoD 规则增强**：支持附件类型、至少 N 份、任选一项、全部清单、金额计算结果、签收确认、动态表单字段联动。
6. **OwnerResolver 扩展**：销售轮询并跳过离岗、直属主管、分管合伙人、案件一级/二级律师、案管组、执行部长、候选领取池。
7. **业务规则配置**：T0 次数、渠道差异、折扣层级、无效标签规则、收费节点、风险代理计算方式不得写在模板 SQL 或 Service 常量中。

### 3.2 P1 组件

- 流程模拟与模板发布前校验；
- 历史实例规则快照对比；
- SLA 批量重算的受控工具；
- 运营看板按业务线、模板、Owner、部门、渠道分组；
- 待办与业务页面的统一动态表单渲染；
- 高风险动作电子签/二次认证接口。

## 6. 两阶段实施计划

### 阶段一：销售主链路 + 案管分类 + 综法最小闭环（建议 8~10 周）

1. 冻结 Q-001、Q-004、Q-005、Q-007、Q-008、Q-010、Q-011、Q-012 的业务口径。
2. 建立字典、业务标签、文件中心最小版和规则配置表。
3. 完成线索标签确认、无效分级、首联/重试、5天跟进。
4. 完成报价/冲突、合同签章、时间型与节点型应收。
5. 完成 11 项转案材料、二次冲突、案管分类及路由。
6. 完成综法分配层级、接单、建联、文书、立案、庭审、30日跟进、结案归档。
7. 发布对应 Todo 模板、事件和处理器，补齐 E2E。

阶段一验收：从线索接入到综法归档可全程由待办驱动；业务状态与待办状态一致；重复事件无重复待办；关键文件受权访问；SLA 和高风险动作可审计。

### 阶段二：非诉 + 执行 + 风险代理 + 绩效与合规增强（建议 6~8 周）

1. 冻结 Q-002、Q-003、Q-006、Q-009 及剩余收费/组织口径。
2. 上线非诉四类业务、成果交付、签收和直接结案。
3. 上线执行接单、强执、执行局、服务分流和周期上报。
4. 上线风险代理计算与销售催收闭环、终止退款。
5. 上线绩效规则版本、计算、复核和重算。
6. 完善文件版本、下载审计、电子签、运营报表和流程模拟。

阶段二验收：三条业务线均形成事件—待办—业务动作—下一待办闭环，绩效/收费结果可追溯，合规审计覆盖 PRD 高风险动作。

## 8. 风险与边界

- PRD 本身仍标记“待业务确认”，Q-001~Q-012 不是研发可自行推断的细节。
- 外呼/APP 未确认前，只建设适配器、回调协议和人工补录，不把具体供应商写死。
- “非诉无需档案管理员归档”不等于无需电子留存。
- 案件业务状态必须由业务 Service 落库；Todo Engine 负责工作编排，不能以完成待办替代业务事实。
- 旧的 14 个标准模板不得原地修改已发布版本，应新建版本并只影响新实例。
