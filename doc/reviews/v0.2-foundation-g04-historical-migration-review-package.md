## 1. 评审目的与边界

本评审包用于关闭 G-04“历史案件默认业务线、历史待办旧版本迁移方案明确”的技术设计缺口。它固定历史盘点、无法自动分类案件清单、批次幂等、校验和受保护回滚方案，供架构、案管和 DBA 在同一提交上复核。

本文件不是可直接部署的 Flyway，也不构成业务结论或迁移批准。默认业务线只能由授权的产品/案管责任人决定；数据库执行方案必须由 DBA 复核；不得由开发人员代签。评审完成前：

- `HISTORICAL_CASE_DEFAULT` 必须保持 `NEEDS_DECISION`；
- 四项迁移证据必须保持 `NEEDS_EVIDENCE`；
- `biz_case.business_line` 不得由本评审包或其引用迁移创建；
- 不得修改历史案件或历史 Todo 实例；
- `G04-HISTORICAL-MIGRATION` 必须保持非批准状态；
- Foundation 总门禁必须保持 `NOT_ADMITTED`。

## 3. 预检盘点与无法分类案件清单

以下 SQL 只读，可在 v0.15 基线或迁移演练库执行：

```sql
select count(*) active_case_count
from biz_case
where del_flag='0';

select count(*) deleted_case_count
from biz_case
where del_flag<>'0';

select coalesce(case_status,'<NULL>') case_status,
       coalesce(case_type,'<NULL>') case_type,
       count(*) case_count
from biz_case
where del_flag='0'
group by coalesce(case_status,'<NULL>'),coalesce(case_type,'<NULL>')
order by case_count desc,case_status,case_type;

select count(*) orphan_todo_version_count
from todo_instance i
left join todo_template_version v on v.version_id=i.template_version_id
where v.version_id is null;
```

案管必须从目标数据集导出无法自动分类清单。导出文件必须至少包含：

```text
case_id,case_no,case_name,case_type,case_status,contract_id,main_lawyer_id,dept_id,
proposed_business_line,exception_reason,review_status,reviewer_user_id,reviewed_at
```

要求：

1. `case_id` 唯一且与导出时数据库一致；
2. `review_status` 只能为 `PENDING`、`RESOLVED` 或 `EXCLUDED`；
3. `RESOLVED` 必须提供三项允许值之一；
4. `PENDING/EXCLUDED` 在批次中不得被默认值覆盖；
5. 导出文件需记录行数、生成 SQL、生成时间、数据库标识和 SHA-256；
6. Reviewer 对文件计算 `Get-FileHash -Algorithm SHA256`，并将结果登记到第 8 节。

### 3.1 已实现的只读预检与候选证据导出

当前分支已提供生成“待分类候选证据”的受控能力，但它不等于第 8 节的签字异常清单：

- `GET /todo/foundation-migration/preflight?gateCode=G-04` 使用 `todo:admission:view`，返回活动/删除案件数、历史 Todo 数、孤儿版本引用数和按案件状态/类型分组的只读库存；
- `GET /todo/foundation-migration/exception-export?gateCode=G-04` 使用独立的 `todo:admission:export` 权限；`V0_20_27` 只登记权限且不自动授予任何角色；
- 导出通过真实 MyBatis 游标按 `case_id` 顺序读取活动案件，只包含本节固定的八个来源字段；服务在 `REPEATABLE_READ` 只读事务内校验游标行数必须与同一快照的活动案件数一致；
- 响应为 `g04-historical-case-preflight.zip`，包含带 UTF-8 BOM 的 `historical-case-exceptions.csv` 和 `manifest.json`；Manifest 使用 `LinkedHashMap` 固定以下键顺序和值：`schemaVersion=1`、`gateCode=G-04`、`fileName=historical-case-exceptions.csv`、`rowCount`、`csvSha256`、`generatedAt`、`classificationState=UNREVIEWED`、`allowedBusinessLines=[NON_LITIGATION,COMPREHENSIVE,EXECUTION]`；
- CSV 对引号、换行和空值按 RFC 4180 风格转义；以 `= + - @ TAB CR` 开头的值会先加单引号，防止表格公式执行；候选行的业务线、Reviewer 和签字字段保持空白，不能被误读为分类结论；
- HTTP 返回行数与 CSV SHA-256 元数据，并设置 `no-store`/`nosniff`；浏览器仅在拥有导出权限时显示按钮，下载后显示行数、校验和与 `UNREVIEWED`。若响应 Content-Type 为 JSON/problem+json，即使 HTTP 状态为 200，也会按 UTF-8 解析稳定业务码/消息并在本地拒绝，不调用保存、不写最近成功元数据，原准入和预检内容保持可见；
- 控制器不会使用在 `StreamingResponseBody` 返回时提前成功的切面日志；它先捕获操作人/部门/IP/URI/方法，再在延迟回调复制并关闭成功后记录 `SUCCESS`，或在传输/关闭失败后记录 `FAILURE`。日志仅含行数、结果和通用失败说明，不含案件名、CSV/响应正文、临时路径或哈希；审计本身失败不会覆盖传输结果；
- ZIP/CSV 只在创建后经 `toRealPath()` 得到且逐次复核的专用规范化根目录内创建；创建文件的真实父目录和路径必须仍位于该根目录，符号链接换靶会被安全拒绝。成功、生成失败、客户端写出失败和显式关闭路径均在同一次清理中最多尝试三次删除；永久失败登记安全的 JVM 退出兜底，公开错误不泄露临时路径或证据内容，后续关闭保持幂等。

`HistoricalMigrationPreflightEndToEndTest` 在 MySQL 8.4 上从精确 v0.15 十一文件基线执行完整 Flyway 至 `0.20.27`，插入会回滚的活动/删除案件夹具（覆盖空值、中文、引号、换行和公式前缀），再调用真实预检服务、MyBatis 游标和归档 Writer。测试逐字节校验 CSV、Manifest 的完整键顺序/值和 SHA-256，并对导出前后的完整有序 `biz_case`、`todo_instance`、八项 G-04 要求、`G04-HISTORICAL-MIGRATION`、Q-001 以及 Todo 孤儿版本计数执行 Java 对象等值比较；关闭后专用临时目录为空，夹具通过 JDBC 事务回滚且另开连接复核为 0。归档 Writer 的符号链接/规范化根目录专项在支持符号链接的 Linux 容器中为 10/10 通过、0 跳过；Windows 全量运行中两项仅在操作系统未提供符号链接创建能力时通过显式 capability assumption 跳过。

该技术证据实测仍为：`biz_case.business_line` 不存在；G-04 来源为 `3 CONFIRMED + 1 NEEDS_DECISION + 4 NEEDS_EVIDENCE`；Q-001 和 `G04-HISTORICAL-MIGRATION` 均为 `OPEN`；Foundation 为 `2/8 NOT_ADMITTED`。候选 ZIP 的 `UNREVIEWED` 状态明确表示它尚未被案管分类、架构/案管/DBA 演练或独立 Reviewer 签字。

## 5. 参数化批次与幂等/断点续跑算法

未来迁移执行器必须接收两个外部输入：`p_batch_key` 与经签字的 `p_default_business_line`。执行入口首先校验默认值：

```sql
if p_default_business_line not in ('NON_LITIGATION','COMPREHENSIVE','EXECUTION') then
  signal sqlstate '45000' set message_text='Reviewed historical default business line is required';
end if;
```

核心批次逻辑如下；它是评审算法，不是当前 Flyway：

```sql
set v_migrated_at=current_timestamp(6);

insert into biz_case_business_line_migration_batch
(batch_key,default_business_line,status,source_case_count,pending_exception_count,
 exception_evidence_sha256,started_at,created_by)
select p_batch_key,p_default_business_line,'PREPARED',
       (select count(*) from biz_case where del_flag='0' and business_line is null),
       (select count(*) from biz_case_business_line_exception where review_status in ('PENDING','EXCLUDED')),
       p_exception_evidence_sha256,v_migrated_at,p_actor
where not exists(
  select 1 from biz_case_business_line_migration_batch where batch_key=p_batch_key
);

select batch_id,status into v_batch_id,v_batch_status
from biz_case_business_line_migration_batch
where batch_key=p_batch_key
for update;

if v_batch_status not in ('PREPARED','RUNNING') then
  signal sqlstate '45000' set message_text='Migration batch cannot be resumed from its current status';
end if;

update biz_case_business_line_migration_batch
set status='RUNNING',started_at=coalesce(started_at,v_migrated_at)
where batch_id=v_batch_id and status in ('PREPARED','RUNNING');

insert into biz_case_business_line_migration_audit
(batch_id,case_id,old_business_line,new_business_line,migration_reason,old_update_time,migrated_at)
select v_batch_id,c.case_id,c.business_line,
       case when e.review_status='RESOLVED' then e.resolved_business_line else p_default_business_line end,
       case when e.review_status='RESOLVED' then 'REVIEWED_EXCEPTION' else 'REVIEWED_DEFAULT' end,
       c.update_time,v_migrated_at
from biz_case c
left join biz_case_business_line_exception e on e.case_id=c.case_id
where c.del_flag='0'
  and c.business_line is null
  and (e.exception_id is null or e.review_status='RESOLVED')
  and not exists(
    select 1 from biz_case_business_line_migration_audit a
    where a.batch_id=v_batch_id and a.case_id=c.case_id
  );

update biz_case c
join biz_case_business_line_migration_audit a on a.case_id=c.case_id and a.batch_id=v_batch_id
set c.business_line=a.new_business_line,
    c.update_by=concat('migration:',p_batch_key),
    c.update_time=a.migrated_at
where c.business_line is null;

update biz_case_business_line_migration_batch
set status='COMPLETED',
    migrated_case_count=(select count(*) from biz_case_business_line_migration_audit where batch_id=v_batch_id),
    completed_at=current_timestamp(6)
where batch_id=v_batch_id and status='RUNNING';
```

幂等规则：

- `batch_key` 唯一，同一签字批次只生成一个批次记录；
- `(batch_id,case_id)` 唯一，同一案件在同一批次只生成一条审计；
- 更新只处理 `business_line is null` 的行；
- `PENDING/EXCLUDED` 异常不进入审计和更新；
- 失败后使用同一 `batch_key` 续跑，已审计或已更新行不会重复生成；
- 不允许用新 `batch_key` 绕过尚未关闭的旧批次。

## 7. 受保护回滚设计

回滚只允许恢复“当前值和更新时间仍与该批次写入完全一致”的行，避免覆盖迁移后的案管修改：

```sql
select c.case_id,c.case_no,c.business_line,c.update_time,
       a.new_business_line,a.migrated_at
from biz_case c
join biz_case_business_line_migration_audit a on a.case_id=c.case_id
where a.batch_id=@reviewed_batch_id
  and (c.business_line<>a.new_business_line or not(c.update_time<=>a.migrated_at));

update biz_case c
join biz_case_business_line_migration_audit a on a.case_id=c.case_id
set c.business_line=a.old_business_line,
    c.update_by=concat('rollback:',@reviewed_batch_key),
    c.update_time=a.old_update_time
where a.batch_id=@reviewed_batch_id
  and c.business_line=a.new_business_line
  and c.update_time=a.migrated_at;

update biz_case_business_line_migration_batch
set status='ROLLED_BACK',completed_at=current_timestamp(6)
where batch_id=@reviewed_batch_id and status='COMPLETED';
```

第一条查询返回的行必须进入人工异常清单，不得强制覆盖。回滚不删除字段、批次、异常或审计记录；后续重新迁移必须使用新的已评审批次和新的证据校验和。

## 9. 受控关闭流程

1. 产品/案管责任人先关闭默认业务线决策并签署异常分类原则；
2. 案管在目标数据集执行第 3 节，生成不可变异常清单和 SHA-256；
