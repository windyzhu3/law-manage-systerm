## 1. 评审目的与边界

本评审包用于 G-05“文件中心最小权限模型通过安全评审”。它把仓库中的对象模型、访问策略、单次令牌、访问审计、清理补偿和 PRD 材料端到端证据汇总为一套可重复验证的输入。

本文件不是安全签字，也不改变数据库审批事实。独立 Reviewer 必须在指定提交上复核代码、执行测试、判断残余风险并登记签字证据；不得由开发人员代签。评审完成前：

- `SECURITY_REVIEW_SIGNOFF` 必须保持 `NEEDS_REVIEW`；
- `G05-FILE-SECURITY` 准入证据必须保持非 `APPROVED`；
- Foundation 总门禁必须保持 `NOT_ADMITTED`；
- 不得通过修改历史 Flyway、直接改库或放宽后端校验绕过评审。

## 3. 必须复核的攻击与越权场景

Reviewer 至少逐项确认以下断言与实际实现一致：

1. 没有匹配的 `FileBusinessAccessChecker` 时，上传/关联/读取默认拒绝；
2. 即使用户能看同一文件的另一条关系，也不能用它读取指定的越权 relation；
3. `PRIVATE` 仅关系用户可见，`DEPARTMENT` 仅关系部门可见，且二者仍需通过底层业务数据权限；
4. 缺失和他人的上传意图返回不可枚举的统一错误，不泄露文件对象或内部键；
5. 访问令牌只保存 SHA-256 哈希，绑定 `relation_id` 与 `actor_id`，过期、重复或并发消费均失败；
6. 令牌兑换时重新执行指定关系的数据权限校验，不能只信任令牌签发时的权限；
7. relation 创建/撤销使用 `actor_id + action_id` 幂等账本和请求指纹，跨关系重放冲突；
8. 本地存储拒绝路径穿越，并在发布前校验字节数与 SHA-256；
9. 预览/下载的打开、成功和失败路径均保留访问审计，审计接口本身受业务访问策略和 `file:object:audit` 约束；
10. 数据库失败、事务回滚和存储清理失败分别产生可追踪生命周期/补偿记录，失败任务可重试。

## 4. 残余风险与必须作出的安全判断

下列能力不应从现有测试中推断为已经解决。Reviewer 必须逐项选择“接受风险、要求部署控制、要求代码整改或不适用”，并说明依据：

| 风险主题 | 当前可见事实 | Reviewer 必须确认的事项 |
|---|---|---|
| MIME/内容识别 | 注册接口接收 `contentType`，下载响应使用已登记类型；当前证据未证明服务端魔数识别或 `nosniff` 防护 | 是否允许信任业务端类型；是否必须增加内容探测、强制下载或 `X-Content-Type-Options` |
| 恶意文件扫描 | 当前仓库证据未包含杀毒、沙箱或隔离区状态机 | 是否由对象存储/网关承担；若无外部控制，是否必须在发布前增加扫描与隔离 |
| 上传大小/容量配额 | 意图会校验期望大小与哈希，但当前 G-05 证据未证明租户/用户/业务对象级容量配额 | 全局 multipart 上限、单文件上限、总容量、并发上传和拒绝服务控制是否满足部署要求 |
| URL 令牌泄露 | 单次令牌位于 `/files/access/{token}` 路径 | 反向代理、APM、访问日志、浏览器历史和错误页是否会记录路径；是否已配置脱敏或需改为安全头/请求体传递 |
| 客户端 IP 可信边界 | 审计通过 `IpUtils.getIpAddr()` 记录来源 | 生产反向代理是否固定可信代理列表，是否会被伪造转发头污染 |
| 存储与备份 | Foundation 提供本地存储适配器和抽象端口 | 正式环境的加密、私有桶/目录权限、备份、保留期、销毁和密钥管理由何处保证 |
| 限流与异常流量 | 当前文件域证据未证明上传、令牌签发或下载的独立限流 | 网关/应用是否已有有效限流、告警和封禁策略 |

任何一项被 Reviewer 判定为高风险且无可接受补偿时，本次结论应为 `REJECTED`，不得批准 G-05。

## 5. 可重复验证命令

在本评审包目标提交的仓库根目录执行：

```powershell
mvn -pl law-file -am test
mvn -pl law-todo -am "-Dtest=FileSecurityReadinessMigrationContractTest,FileSecurityReviewPackageContractTest,TodoFileSecurityReadinessServiceTest,TodoAdmissionEvidenceServiceTest" "-Dsurefire.failIfNoSpecifiedTests=false" test
```

真实 MySQL 8 环境必须从空的 v0.15 基线执行完整 Flyway 链，再运行：

```powershell
mvn -pl ruoyi-admin -am "-Dtest=FlywayMigrationTest,FileMaterialEndToEndTest" "-Dsurefire.failIfNoSpecifiedTests=false" test
```

并检查：

- 终端迁移为本评审包所在版本；
- G-05 固定目录仍为 7 项，其中 6 项 `CONFIRMED`、1 项 `NEEDS_REVIEW`；
- `SECURITY_REVIEW_SIGNOFF` 未被开发迁移改为 `CONFIRMED`；
- `G05-FILE-SECURITY` 准入证据仍为 `OPEN`，且 Owner/Reviewer/截止时间/证据引用未被自动填写；
- 21 类材料逐类完成真实上传、预览、令牌重放拒绝、下载和访问审计。

## 7. 受控关闭流程

1. 产品/安全负责人先在“准入证据”页为 `G05-FILE-SECURITY` 指定有效 Owner、独立 Reviewer、截止时间和本评审包引用；
2. Reviewer 在精确提交 SHA 上完成第 3～5 节复核，形成不可变签字/审批记录；
3. 若结论为拒绝，登记 `REJECTED` 和整改项，G-05 保持阻断；
4. 若结论为通过，维护者新增一个后续前向 Flyway，仅把 `SECURITY_REVIEW_SIGNOFF` 的 `source_status` 更新为 `CONFIRMED` 并指向实际签字证据；不得修改本次或更早迁移；
5. 重新执行真实 MySQL 和全量门禁，确认文件安全目录达到 7/7；
6. 只有预先指定的独立 Reviewer 才能通过受控 API 将 `G05-FILE-SECURITY` 从 `IN_REVIEW` 更新为 `APPROVED`；后端仍会再次校验 7/7 技术/来源状态；
7. 聚合准入继续按 G-01～G-08 全部满足后才能变为 `ADMITTED_FOR_PHASE_ONE_BUSINESS_IMPLEMENTATION`。G-05 单独关闭不代表 v0.2 已准入。
