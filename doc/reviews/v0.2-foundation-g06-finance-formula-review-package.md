## 1. 目的与不可越过的边界

本评审包用于让财务、业务、架构和测试人员在同一份材料上确认节点型收费、应收、催收、退款及风险代理费的事实边界。它不关闭 Q-009/Q-012，不选择金额公式、催收 Owner、金额精度、舍入、税费、退款或重算规则，也不构成可执行 Flyway。

所有业务结论和验收签字必须由授权责任人提供，不得由开发人员代签。评审闭环前：

- `Q-009`、`Q-012` 必须保持 `OPEN`；
- `FINANCE_BUSINESS_SIGNOFF=NEEDS_REVIEW`；
- `G06-FINANCE-FORMULA=OPEN`；
- 不得新增或修改财务业务事实表；
- G-06 必须保持 3/9 READY，Foundation 必须保持 `2/8 NOT_ADMITTED`。

## 3. Q-009 必须形成的不可变决策记录

Q-009 的结论必须逐项回答，禁止用“按合同约定”等无法执行的文本代替：

1. 应收触发类型：时间型、节点型、风险代理型是否均启用；
2. 每个节点的稳定编码、适用业务线、适用案件类型和前置条件；
3. 金额来源：固定金额、合同计划比例、节点比例或外部确认值；
4. 催收 Owner 的解析顺序、角色兜底和无人可分配时的异常队列；
5. 到期规则、工作日历、宽限期、逾期层级和暂停/恢复条件；
6. 部分收款、足额收款、多笔收款、冲销与开票的关系；
7. 重复节点事件的幂等键和是否允许重新打开应收；
8. 终止、转案、结案时未结应收的处理方式；
9. 退款发起、审批、付款、失败和撤销的状态机；
10. 结果事件、Todo Owner 与业务回写的责任边界。

决策附件至少包含：决策编号、版本、适用日期、财务 Owner、业务 Owner、批准人、测试案例引用和 SHA-256。

## 4. Q-012 必须形成的不可变决策记录

Q-012 必须明确系统自动计算与人工录入/审核的边界，并逐项确认：

1. 风险代理适用条件、合同标记和生效时间；
2. 公式版本、变量清单、变量来源与缺失值处理；
3. 风险基数的定义和允许的调整项；
4. 比例、阶梯、上下限和封顶规则；
5. 金额精度与中间值精度；
6. 舍入模式与舍入发生步骤；
7. 含税/不含税口径、税费承担方和开票关系；
8. 退款、终止、撤销、判决变更或回款更正后的重算边界；
9. 自动计算、二级律师填报、一级律师审核、财务复核各自责任；
10. 历史公式版本是否冻结，重算是否产生新版本而非覆盖；
11. 计算结果何时生成 `RISK_FEE_CONFIRMED`；
12. 争议、负数、超上限和缺少来源数据时的异常处理。

不得在 Q-012 关闭前把比例、阶梯、金额精度、舍入或税费规则硬编码到 Service、Todo 模板或迁移 SQL。

## 6. 事件、幂等与审计边界

1. 既有 `PAYMENT_CONFIRMED` 继续代表财务确认回款，不等同催收成功；
2. `RECEIVABLE_DUE` 只能由唯一的应收触发事实生成，幂等键至少绑定规则版本、来源对象和触发窗口；
3. `RISK_FEE_CONFIRMED` 只能由已审核的不可变计算版本生成；
4. 同一业务动作不得同时由 Controller 和 Todo 处理器重复发布事件；
5. 所有金额动作记录操作人、业务时间、入账时间、来源、原值、新值和原因；
6. 退款与冲销使用补偿事实，不删除 `PAYMENT_CONFIRMED` 或历史计算；
7. Todo 只编排“谁在何时完成什么”，财务 Service 持有金额事实和状态机。

## 7. 只读预检与对账 SQL

评审前在目标数据副本执行并保存数据库标识、时间、命令、输出与 SHA-256：

```sql
select confirm_status,invoice_status,count(*) plan_count,
       sum(receivable_amount) receivable_total,sum(received_amount) received_total
from biz_contract_fee_plan
group by confirm_status,invoice_status;

select count(*) negative_amount_count
from biz_contract_fee_plan
where receivable_amount<0 or received_amount<0;

select count(*) over_received_count
from biz_contract_fee_plan
where received_amount>receivable_amount;

select count(*) duplicate_payment_event_key_count
from (
  select idempotency_key,count(*) row_count
  from business_event
  where event_type='PAYMENT_CONFIRMED'
  group by idempotency_key having count(*)>1
) duplicate_keys;
```

未来结构演练还必须验证：

- 六个节点收费字段存在且值域有效；
- 三张支持表和风险计算表存在；
- 应收触发幂等键无重复；
- 催收记录均关联有效应收和 Todo；
- 退款均关联原收款且金额不超过可退余额；
- 风险计算均带公式版本、输入快照、审核人和状态；
- `PAYMENT_CONFIRMED`、`RECEIVABLE_DUE`、`RISK_FEE_CONFIRMED` 无重复幂等键；
- 收费计划、回款、退款和风险费汇总能够逐笔勾稽。

## 8. 回滚、冲销与重算原则

结构迁移在演练阶段可回滚新增的空字段/空表，但一旦产生金额事实，不允许通过删除行或覆盖历史记录回滚。业务纠错必须使用：

- 回款冲销记录；
- 退款补偿记录；
- 风险计算新版本；
- 失效原应收并创建替代应收；
- 对已产生 Todo/事件保留完整关联审计。

重算必须记录旧版本、新版本、触发原因、输入差异、操作者、审批者和时间。是否允许自动重算以及何时需要重新审批，必须来自 Q-012。

## 10. 受控关闭流程

1. 产品负责人为 Q-009/Q-012 分配 Owner、Reviewer 和截止时间；
2. 财务/业务责任人完成第 3、4 节的逐项结论并签字；
3. 架构/DBA 根据签字结论形成独立前向 Flyway，不修改本评审包迁移；
4. QA 在精确提交 SHA 和数据快照上完成并发、幂等、金额勾稽、退款、冲销和重算测试；
5. 财务、业务、架构、DBA 和 QA 登记不可变证据引用；
6. 后续元数据迁移只有在运行态结构真实达到 9/9 时，才可把签字来源提升为确认；
7. 预先指定的独立 Reviewer 才能通过受控 API 审批 `G06-FINANCE-FORMULA`；
8. G-06 关闭不等同 Foundation 总体准入，仍需 G-01～G-08 全部满足。
